> 一句话：  
> **多 Agent 是逻辑协作关系，不是「必须跨机」。**  
> 我们今天的主形态是「同机 Hermes 编排 + 跨机调服务」；A2A 是跨组织互操作时才需要的通信规范，不是当前缺口。

## 0. 四问速答

| 原问题 | 行业口径 | 结合现网后的判断 |
|--------|----------|------------------|
| 多 Agent 是同机还是跨机？ | 两者都是。核心是「多个能独立感知 / 决策 / 行动的智能体协作」，物理部署可集中也可分布。 | **我们两者都有，但主路径是同机。** Hermes 对话循环、`delegate_task` 子代理、Skill、`modules/orchestrator` DAG 都在同一套运行时。跨机的是推理节点、数仓、ES、CVAT、Coral 网关，以及端上扫地机——其中多数是 **Agent → 服务**，不是 **Agent → Agent**。 |
| 多物理机协作有什么协议？常用场景？ | 主流叙事是 A2A（Agent 互操作）+ MCP（工具 / 数据源）+ 消息队列 / 共享黑板。场景常举工业机器人、车队协同、边云分层。 | **现网还没用 A2A。** 跨机走 HTTP / OpenAI 兼容 API / Webhook / MySQL 目录。MCP 已标为演进目标。真正接近「跨机 Agent」的是端云：机端感知 vs 云 / 仓侧推理与编排，但中间协议是采集与任务接口，不是 A2A。 |
| 用 A2A 必须中心注册，还是全网广播？ | 协议本身三种都支持：Well-Known URI（已知地址后解析能力）、中心注册表（企业主流）、DNS-SD（局域网提示）。 | **企业内应预注册，不要全网广播。** 我们已经有等价物：`ai_task_info`（现网推理服务目录）、算子目录、Skill / 资产卡。缺的是跨组织互操作，不是发现协议。 |
| 注册表 / 目录怎么做权限？ | 发现和访问分离。三层：身份认证（OAuth / JWT / mTLS）→ 注册表 RBAC → 调用时授权（scope / ABAC / 能力本地执行）。A2A 不管具体 IAM。 | **原则已对齐，实现按层拆开。** 壳层五角色 YAML 只管「谁能进控制台」；领域取数、Skill、图片出口各有自己的门。目录回答「有什么」，包装器 / 二次确认 / 环境凭证回答「能不能调」。 |

## 1. 部署形态：同机与跨机并存

### 1.1 行业定义（保留有用的部分）

多 Agent 系统的关键特征是 **分布式决策 + 专业化分工**，不是「机器台数」。每个 Agent 有独立的感知、决策、执行，通过约定协议协同，用来突破单 Agent 的上下文窗口、专业能力和容错上限。

协作范式与部署位置无关，常见四种：

| 范式 | 含义 | 现网近似 |
|------|------|----------|
| 编排 / 监督者 | 一个主 Agent 拆任务、盯状态 | Hermes 主循环 + `delegate_task` |
| 流水线 | 固定先后，上一步产物进下一步 | `modules/orchestrator` DAG、看板漏斗 |
| 对等 / 群组 | 角色对等，协商或投票 | 一期不做；知识进化里的「采集 / 整理 / 关联」只是角色切分 |
| 黑板 | 共享工作区，各写各读 | scratch 会话盘、对象 / 表里的中间结果、DatasetHandle |

选型经验也成立：团队小、链路短 → 同机更便宜；跨系统 / 跨组织、要高可用隔离 → 再上跨节点和标准化协议。

### 1.2 现网实际长什么样

```text
同机（同一 Hermes 运行时 / 同一编排进程）
  ├─ 主 Agent：LLM 工具循环
  ├─ 子 Agent：delegate_task（隔离 / 并行时才开）
  ├─ Skill：过程性知识（给模型看怎么做）
  ├─ 算子目录 + DAG：可校验的执行单元
  └─ 记忆 / scratch：按登录名隔离的工作区

跨机（多数是服务，不是对等 Agent）
  ├─ Coral 聚合网关：云端大模型
  ├─ 本机 / 机房 vLLM、标注仓推理节点：小模型 / SAM / VLM
  ├─ ES 网关、Hive、CVAT、闭环 MySQL
  └─ 端侧设备：机端采集与感知（边）
```

对照外部综述里的三类例子：

| 外部常举的场景 | 和我们的真实距离 |
|----------------|------------------|
| LangGraph / CrewAI 同机流水线 | **就是现在的主形态。** 调研 / 写作 / 编辑那种 3–5 个角色，对应我们的 Skill + 子代理 + DAG，不必先上 A2A。 |
| 工业机器人集群靠 A2A 调度 | **部分像，协议不像。** 产线侧我们有 AGV / 扫地机集群和标注仓 GPU 节点，但调度器是 cvat_server + 既有任务接口，不是 Agent Card。 |
| 自动驾驶多车 A2A | 不在本工程范围。不要用它论证当前要上 A2A。 |
| 边云：端侧小模型 + 云端大模型 | **最贴近。** 机端感知、仓侧 / 云侧复杂推理。中间是采集协议、任务下发、模型服务 HTTP，不是 A2A + MCP 套件。 |

### 1.3 判断标准（避免被「多 Agent」带偏）

问自己三件事，比问「同机还是跨机」有用：

1. **对方有没有独立决策？** 有 → 才是 Agent；只是按契约跑推理 / 查表 → 是工具或服务。
2. **要不要互相发现、委托任务、跟踪生命周期？** 要，且跨团队 / 跨语言 / 跨云 → 才值得谈 A2A。
3. **失败时谁负责降级？** 同机编排可以把重试、门控、预算预检做在 DAG 里；跨机对等 Agent 要把这些写进协议和策略。

现网结论：W1/W2/S1 的验收卡在 **编排引擎 + 数据层**，不卡在跨机 Agent 协议。

## 2. 跨物理机协作：协议栈要拆开看

### 2.1 行业主流叙事

外部综述把跨机栈写成：

```text
A2A     Agent ↔ Agent 的任务委托、能力发现、产物传递（常被比喻成「TCP」）
MCP     Agent ↔ 工具 / 数据源（常被比喻成「HTTP」）
MQ      Kafka / RabbitMQ / RocketMQ：任务与状态解耦
黑板    MinIO / OSS / Redis：大文件和中间结果
IoA     IETF 草案：动态组队、去中心协作（观察即可）
AWCP    把远程工作区当文件系统投影（观察即可）
```

这个分层 **方向对**，但两个比喻不要当真：

- A2A 不是传输层。它是基于 HTTP + JSON-RPC 2.0 的应用协议，管 Agent Card、Task、Artifact。
- MCP 也不是传输层。它是工具与上下文的统一接口。现网大量「跨机」其实已经是 MCP 要解决的那一类问题（调 ES、Hive、文件系统、推理 HTTP），只是还没换成 MCP 外壳。

### 2.2 必须先分清的两件事

| | Agent → Agent（A2A 领地） | Agent → 工具 / 服务（MCP 领地） |
|--|---------------------------|--------------------------------|
| 对方 | 另一个会拒绝、会追问、会自己拆任务的智能体 | 按 schema 执行的 API / 模型 / 库 |
| 现网例子 | 理论上：Hermes 委托给另一套业务 Agent；端上若有 onboard 决策体 | Coral、vLLM、`ai_task_info` 指向的推理服务、ES / Hive / CVAT 包装器 |
| 当前要不要上标准协议 | **暂不上。** 没有第二套对等 Agent 运行时要对齐 | **演进目标。** 先把包装器契约稳住，MCP 是统一外壳，不是第一块砖 |

外部材料里的「工业机器人 / 多车 / 边云都在用 A2A」，应当读成 **目标架构故事**，不是我们仓库里的已实现事实。

### 2.3 现网协议地图

| 链路 | 实际协议 | 对应行业格子 | 备注 |
|------|----------|--------------|------|
| Hermes ↔ Coral / 百炼 / 本地 vLLM | OpenAI 兼容 HTTP | 模型调用，不是 A2A | 云端推理与本地推理按数据域切开 |
| Hermes ↔ 标注仓推理 | 读 `ai_task_info`，以后只绑 `task_name`；启动容器走 `/aiShell/startDocker`；任务下发是 `/aiTask/*`（包装器冻结，禁止擅自 POST） | 服务目录 + RPC | 调度器仍是 cvat_server，不要和 Hermes DAG 写成一套进程 |
| Hermes ↔ ES / Hive | 环境变量 + 槽白名单包装器 | 接近 MCP 工具 | 无 env 不发请求；Chat 不吐裸 SQL |
| Hermes ↔ CVAT | 确认后的受控 POST | 写操作工具 | 须余量 > 0 且二次确认 |
| 知识库新鲜度 | Git + Webhook | 不是 MCP | MCP / GitLab Server 是下一阶段 |
| 大结果 / 回放 | DatasetHandle（引用，不内联千万级数据） | 黑板的弱形式 | 节点传句柄不传数据本体 |
| 端侧采集 | 既有采集协议 / ES `ai_collect` | 边云数据面 | 不要改口成 A2A |

### 2.4 常用场景：外部例子如何翻译

**工业产线协同。** 徐工那类「离线编程 + 感知 + AGV 调度、延迟 < 200ms」证明的是 **控制面与数据面要近、目录要准、避障要本地**，不是证明必须上 Google A2A。我们对应的是：机端建图 / 避障在端上，场景挖掘与标注调度在仓侧，目录用 `ai_task_info` + `ai_server_info`。

**边云分层。** 这是现网最该讲的故事：端侧小模型做本地感知，仓侧 / 云侧大模型做复杂描述与编排。分层已经存在；缺的是统一工具外壳和调用审计，不是再发明一种 Agent 互发现。

**内容流水线 / 知识进化。** 采集、整理、关联在现网是 Skill 或 Cron 角色，不是已经在跑的 Hermes 子智能体群。`delegate_task` 只在要隔离或并行时用。

## 3. A2A 的注册与发现，以及我们已有的等价物

### 3.1 协议里的三种策略

A2A **不强制**「必须先在某个中心挂号」，也不等于「向全网广播自己」。

| 策略 | 它到底回答什么 | 适用 | 不适用 |
|------|----------------|------|--------|
| Well-Known URI `/.well-known/agent-card.json` | **解析**：这个已知地址上的 Agent 会什么 | 点对点、调用方已有 URL | 大规模动态发现。IETF 也强调这是 resolution，不是 discovery |
| 中心注册表（Nacos / 企业 Catalog） | **发现**：现在有哪些 Agent、能力是什么 | 企业、要审计、要负载与故障转移 | 把注册表当成授权中心 |
| DNS-SD（局域网 mDNS，服务类型 `a2a`） | **提示**：附近可能有谁 | 开发机、同网段实验室 | 生产外网；发现通道本身不建立信任 |

补充一条行业原则（Microsoft 的说法，值得留下）：

> **Discovery before access and policy enforcement。**  
> 注册表只负责「谁在这里」，不负责「谁可以调用谁」。

### 3.2 现网已经在用「预注册」，只是不叫 A2A

| 现网目录 | 登记的是什么 | 更像哪种发现 | 谁来消费 |
|----------|--------------|--------------|----------|
| `ai_task_info` + `ai_server_info` | 在用的推理服务、节点 IP / 卡、端口 | 中心注册表 | 以后 Hermes 组 DAG 只绑 `task_name`，不写死 host:port |
| 算子目录 `skills/operators/*.json` | 带类型的执行单元、成本、证据类型 | 封闭 Catalog | 规划器只能从里面挑，不能自由写码 |
| Skill 配置档 / `sync-to-hermes.sh` | 过程性知识包 | 预装清单 | Chat 按 profile 加载 |
| 语义资产卡 `skills/assets/` | 能力意图、边界、权限、版本 | Agent Card 的弱形式 | **说明书，不是运行时协议，也不是 MCP** |
| MCP `mcp_servers`（profile） | 外部工具进程 | 预注册，可动态刷新 | 演进位；Python 工具仍是 import 期静态注册 |
| 知识库 Git 仓 | 事实源路径与 front-matter | 内容目录，不是 Agent 目录 | `kb.retrieve` |

所以第三个原问题换成现网语言是：

- **要预先登记吗？** 对内：要。推理服务、算子、Skill、资产卡都是预注册，还带人工评审。
- **要向全网广播吗？** 不要。内网目录 + 已知基址即可。Well-Known / DNS-SD 只适合实验室点对点。
- **要上 A2A Registry 吗？** 只有出现「另一套独立 Agent 运行时要互相委托任务」时才值得。现在把 `ai_task_info` 和算子目录维护对，收益更大。

### 3.3 发现流程（现网 vs A2A 教科书）

```text
教科书 A2A
  Provider 注册 AgentCard → Registry 查询 → 再按 Card 里的 URL 远程调 Task

现网（一期）
  人把算子 / Skill / task_name 登记进目录
    → 编排器或模型只从目录挑
    → 包装器按 env / 白名单 / 二次确认真正发请求
    → 大结果只传 DatasetHandle
```

两边都遵守「先发现、后访问」。差别是：我们发现的是 **服务与算子**，不是对等 Agent。

## 4. 注册表 / 目录的权限控制

### 4.1 行业三层（可直接当检查清单）

A2A 规范 **不定义** 认证实现，只要求走既有 Web 安全。平台自己补齐：

| 层 | 行业常见做法 | 管什么 |
|----|--------------|--------|
| L1 身份 | OAuth 2.0、JWT + JWKS、mTLS、API Key | 你是谁 |
| L2 目录 RBAC | admin / editor / viewer（GCP Agent Registry、Entra 同类角色） | 谁能登记、改元数据、看见目录 |
| L3 调用授权 | JWT scope、RBAC+ABAC、会话里互验、能力范围本地执行 | 这次能不能用这个 skill / 这批数据 |

会话级流程可以记四步：发起（带可验证凭证）→ 互验并确认能力被本地策略允许 → 数据直连、两端各自强制范围 → 终止或过期。生产上还要工作空间 / Collection 隔离，避免「看见了就能调」。

### 4.2 现网已经按层拆开（不要并成一张表）

壳层合同原文就写了四层，和行业三层能对上，只是多拆了一层「领域能力」：

```text
L1  入口身份     WebUI / Dashboard ← dashboard-rbac.yaml
                 飞书 ← FEISHU_ALLOWED_USERS（另一套，勿开全员）
L2  功能可见性   侧栏 / 设置分段裁剪（裁剪 ≠ 围墙）
L3  写接口硬闸   目前几乎只有 /api/rbac/* ；直调 cron / 密钥仍是已知缺口
L4  领域能力     ES / Hive 槽白名单、Skill 整包、A4 图片出口与 KB 写
                 —— 不跟控制台账号绑
```

对照行业注册表：

| 行业层 | 现网落点 | 明确不管什么 |
|--------|----------|--------------|
| 身份认证 | 本地 YAML 账号 + session；飞书独立白名单 | 公司 SSO 未做 |
| 目录 RBAC | 五角色管控制台；算子 / `ai_task_info` 的写入是人审 + 库权限，不是 Agent 自注册 | 访客能进对话 ≠ 能改目录 |
| 调用授权 | 包装器 env、槽白名单、余量与二次确认、A4 Token 与审计 | 一期 **不按角色** 拆「只许检索 / 不许建任务」 |

资产卡上的「权限」字段是给模型看的边界说明，**不会在运行时强制执行**。真正挡请求的是包装器和环境凭证。

### 4.3 现网缺口（讲权限时要主动说）

1. **L2 不是围墙。** 非 admin 仍可能直调部分后端。全站按 `scopes` 返回 403 是下一期。
2. **发现了 ≠ 能调用。** `ai_task_info` 可只读核对，`/aiTask/*` 包装器冻结；没有基址、没有用户点头，禁止 POST。
3. **换人也不换 Skill 面。** 算法和访客只要都能进对话，模型看到的工具面目前一样。这是产品选择，不是协议缺陷。
4. **不要用 A2A 会话套件来补这些洞。** 先把壳层 L3 和领域 L4 的硬闸补齐，比引入一套新的 Agent 互信更便宜。

## 5. 对外部综述的纠偏（避免原样转发）

1. **「A2A = 跨机通信的 TCP」** 过满。A2A 是互操作与任务生命周期规范；传输仍是 HTTP。我们跨机已经在用 HTTP，并不缺一层「TCP」。
2. **「跨机就必须 A2A + MCP」** 过满。跨机调模型 / 数据库 / 标注服务，MCP（或等价包装器）就够。A2A 只在出现对等 Agent 时才必要。
3. **「Well-Known 是自注册发现」** 用词不准。它是已知 URL 上的能力解析，调用方仍要先知道地址。
4. **「向全网广播自己的存在」** 不适合企业现网。DNS-SD 最多当实验室提示，信任仍靠 Card 校验和调用鉴权。
5. **IoA / AWCP** 记一笔即可，不要写进选型结论。
6. **徐工 / 多车例子** 用来解释边云和低延迟控制面，不要当成「所以我们要上 A2A v1.0」。

## 6. 现网选型建议

按时间从近到远，不按热度：

| 阶段 | 做什么 | 不做什么 |
|------|--------|----------|
| 现在 | 维持同机编排；目录用算子契约 + `ai_task_info`；跨机继续走包装器 HTTP；权限按 L1–L4 分开讲 | 不上 A2A Server / Registry；不把 Skill 改造成 Agent Card 对外暴露 |
| 下一步 | 包装器稳定后，把对外工具逐步收成 MCP（一次集成、多入口复用）；补 L3 硬闸和调用审计 | 不把 Obsidian 桌面 MCP 当服务端发现方案（容器里没有桌面会话） |
| 出现第二套对等 Agent 时 | 控制面放到独立项目 **SUNNY**（策展目录 + sidecar），线协议仍后做 | 不从 DNS-SD / 全网广播起步；不在 AIDataAgent 仓内自建 Registry |

一句话留给对外沟通：

> A2A 定义 **Agent 怎么交互、怎么描述自己、怎么管任务生命周期**；  
> 不定义注册中心怎么实现、权限规则怎么写、信任怎么建立。  
> 我们今天缺的是把 **服务目录、调用门禁、编排契约** 做扎实；等真有跨运行时的 Agent 委托，再在这套目录上加 A2A，而不是反过来用协议倒逼架构。

## 7. 术语对照

| 对外 / 面试说法 | 现网对应物 | 不要说成 |
|-----------------|------------|----------|
| Multi-agent | Hermes 主循环 + 子代理 + DAG 角色 | 已经在跑跨机 A2A 集群 |
| Agent Card | 资产卡 + 算子 JSON + `ai_task_info` 行 | 已实现 A2A Card |
| Registry | `ai_task_info` / 算子目录 / Skill profile | Nacos A2A Registry |
| MCP | 演进中的统一工具面；现网是 Python 包装器 | 知识库主路径已经是 MCP |
| 黑板 | scratch + DatasetHandle + 对象 / 表 | 已上 Redis 黑板 |
| 零信任发现 | 目录可查、调用另鉴权 | 注册表即授权 |
