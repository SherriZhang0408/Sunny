# 定位：SUNNY 在多 Agent 栈里站在哪

> 给要参考本仓的开发者。行业口径压成可落地判断，不是协议实现说明书。近亲仓库、学什么、不抄什么见 [同类项目对照](./同类项目对照.md)。现行合同仍是 [ADR-001](../decisions/ADR-001-开写前五件事.md)。

| 项 | 内容 |
|----|------|
| 日期 | 2026-10-08（公开改写；初稿 2026-09-18） |
| 性质 | 定位说明 |
| 本仓 | 企业内策展型 Agent 注册中心。发现谁在、会什么、谁看得见；调用另发短时票，直打对方 sidecar |

> 一句话：  
> **多 Agent 是协作关系，同机编排和跨运行时目录是两层。**  
> SUNNY 只做第二层：名片、目录、审批、短时票。任务怎么拆、对话怎么转，留在各智能体自己的运行时。

---

## 0. 四个常见问题

| 问题 | 行业口径 | SUNNY |
|------|----------|-------|
| 多 Agent 是同机还是跨机？ | 两者都是。关键是多个能独立决策的智能体协作，不是机器台数。 | 同机编排不进本仓。本仓解决的是跨运行时：对方已有 HTTP，旁边挂 sidecar，用名片互相发现。 |
| 跨机用什么协议？ | 常见叙事是 A2A（Agent 互操作）+ MCP（工具 / 数据源）+ 消息队列 / 共享黑板。 | 名片字段对齐 A2A Agent Card。发现面可以是 REST，也可以是只读 MCP。调用是短时票 + 直打 sidecar，不实现完整 A2A Task 生命周期，也不当消息总线。 |
| 必须中心注册，还是全网广播？ | A2A 三种都允许：Well-Known（已知地址后解析能力）、中心注册表（企业主流）、DNS-SD（局域网提示）。 | 企业内预注册。已实现中心目录和 Well-Known 拉取。不做 DNS-SD，不向公网广播。 |
| 目录怎么做权限？ | 发现和访问分开。身份认证 → 目录 RBAC → 调用时再授权。A2A 不规定具体 IAM。 | Hub 登录是会话；调用票另签，绑调用方、技能和 Card 版本。看见名片不等于能调。 |

## 1. 同机编排和跨运行时目录

多 Agent 的特征是分布式决策和专业化分工。协作范式与部署位置无关，常见四种。SUNNY 只碰到最后一列里写明的部分。

| 范式 | 含义 | 谁来做 |
|------|------|--------|
| 编排 / 监督者 | 一个主 Agent 拆任务、盯状态 | 调用方自己的运行时（CrewAI、LangGraph、AgentScope、明略 Octo 这一层） |
| 流水线 | 固定先后，上一步产物进下一步 | 同上 |
| 对等 / 群组 | 角色对等，协商或投票 | 本仓不做群聊和投票 |
| 黑板 | 共享工作区，各写各读 | 本仓不提供共享盘。可选 `workspace` 只是名片上的可见范围标签 |

判断是不是该进 SUNNY，看三件事：

1. 对方有没有独立决策。只按契约查一次 HTTP，是工具或服务，名片上写成一个 skill 即可。
2. 要不要跨团队互相发现、按技能授权。要，才登记。只在同一个进程里拆角色，不必进目录。
3. 失败时谁降级。重试和预算留在调用方。本仓负责的是：搜不到、出不了票、票过期、卡被停用或弃用。

## 2. 协议栈怎么拆

```text
A2A     Agent 怎么描述自己、任务怎么委托。基于 HTTP + JSON-RPC，不是传输层
MCP     Agent 怎么调用工具、怎么读上下文。也不是传输层
目录    谁在、会什么、谁看得见、版本与心跳
数据面  真正转发调用、限流、统一审计。本仓不做
```

两个常见比喻不要当真：

- A2A 不是「跨机通信的 TCP」。传输仍是 HTTP。SUNNY 用它的 Agent Card 当名片格式，调用路径是 REST invoke。
- MCP 不是「所有跨机调用的 HTTP」。本仓的 MCP 只暴露发现面（搜目录、读名片、读变更），不签发票、不代调。

| | Agent → Agent | Agent → 工具 / 服务 |
|--|----------------|---------------------|
| 对方 | 会拒绝、会声明自己会什么的智能体 | 按 schema 执行的 API |
| SUNNY | 名片 + 审批 + 短时票 + sidecar | 同一个 skill 模型。写操作和 `execute_sql` 默认不对对等开放 |

## 3. 发现的三种策略，本仓取了两种

A2A 不强制先在某个中心挂号，也不等于向全网广播。

| 策略 | 回答什么 | SUNNY |
|------|----------|-------|
| Well-Known `/.well-known/agent-card.json` | 这个已知地址上的 Agent 会什么 | sidecar 挂完整卡；Registry 可按基址拉取。这是解析，不是全网发现 |
| 中心注册表 | 现在有哪些 Agent、能力是什么 | 本仓的主路径。要审计、要审批、要心跳 |
| DNS-SD | 附近可能有谁 | 不做。局域网提示建立不了信任 |

行业原则（Microsoft 对 Agent Registry 的说法，本仓照此实现）：

> Discovery before access.  
> 注册表回答「谁在这里」，不回答「这次能不能调」。

调用方拿到公开卡之后，还要短时票。`private`、待审批、`restricted`、`write`、已弃用，对等出不了新票。

## 4. 权限按三层看

A2A 不定义认证实现。本仓目前的落点：

| 层 | 管什么 | 本仓 |
|----|--------|------|
| 身份 | 你是谁 | Hub 本地账号（管理员 / 开发者）。公司 SSO 还没做 |
| 目录 | 谁能登记、改卡、看见目录 | 管理员全权限；开发者维护自己发布的卡；不能自己把待审批卡改成已通过 |
| 调用 | 这次能不能用这个 skill | HMAC 短时票，绑调用方 `agent_id`、被调技能、`card_version`。登录会话不能当调用票 |

工作区隔离见 [ADR-002](../decisions/ADR-002-工作空间隔离.md)：调用身份是 Agent 服务账号，不进个人 scratch。

---

## 5. 读外部材料时的纠偏

1. 「跨机就必须 A2A + MCP」过满。跨运行时调一个已有 HTTP，名片 + sidecar 就够。完整 A2A Task 只在双方都要任务生命周期时才必要。
2. 「Well-Known 是自注册发现」用词不准。调用方仍要先知道基址。本仓的自注册走 enroll，和 Well-Known 拉取是两条路。
3. 「向全网广播自己的存在」不适合企业目录。信任来自登记、审批和调用票。
4. 工业机器人、多车、边云的故事说明控制面和数据面要分开。不要把它读成「所以要上公网 A2A Registry」。
5. IoA、AWCP、DHT 联邦记一笔即可，不进选型。
6. 编排框架和 IM 协作网回答的是「谁拆任务」。它们可以当调用方，不是本仓要替换的产品。

---

## 6. 现在的边界

已经有的：登记、搜索、心跳、探活、Well-Known 拉取与 A2A 导出、审批、短时票、sidecar 映射、只读 MCP、弃用与升版变更流、示例租户 `lab.echo`。

刻意不做：调用网关、对话入口、官方 MCP 商店、公网市场、公司 SSO、外置 agentgateway（数据面以后可以外接，不嵌进 Registry）。
