项目介绍

连接企业内分散的智能体能力

SUNNY 建立统一的能力发现与访问控制面，让智能体在不迁移数据、不绕过权限的前提下开展协作。

核心判断 企业缺少的不是更多智能体，而是让现有智能体彼此发现并受控协作的机制。

执行摘要

企业智能体通常建设在不同业务系统中。每个智能体掌握不同数据，也受不同账号、审批和审计规则约束。当前它们大多只能被所在系统内的用户使用，其他智能体既不知道其能力，也没有标准方式判断是否可以访问。

SUNNY Agent Hub 将这些智能体组织成一个可治理的能力目录。它登记“谁会什么、在哪里、谁能看见、如何申请访问”，并通过短时调用票和目标侧 sidecar 建立受控调用链。

一句话定位

企业内策展型 Agent 注册中心与调用控制面。

关键边界

发现不等于访问。Registry 不代理业务流量，数据和最终执行权限仍留在原系统。

现状：能力存在，但组织不可见

智能体已经分布在企业各处，阻碍协作的是跨系统发现、权限表达与接入成本。

经营分析系统 数据分析智能体

经营指标、报表数据

数据权限 + 查询审计
流程审批系统 审批智能体

流程状态、审批动作

角色权限 + 人工审批
研发与运维系统 运维智能体

服务状态、变更能力

环境权限 + 操作审计
不可发现 没有统一名片 没有访问说明 只能点对点接入
重复建设

同类能力被多次开发，已有能力难以复用。

集成脆弱

地址、鉴权和参数写死，接口变化牵动调用方。

治理失焦

能力边界、审批状态和版本缺少统一视图。

协作受阻

一个智能体无法主动找到可用的企业能力。

从能力网到智能体网络

单个智能体依赖自己能访问的数据和自身权限，通过 Tools 与 Skills 完成一个或若干任务。多个智能体用握手协作，每张能力网仍留在各自节点上。

方案：在现有系统之上增加控制面

SUNNY 不建设新的数据孤岛，而是用标准名片、策略门闩和薄适配器连接已有智能体。

使用入口 用户、业务智能体、开发工具、MCP 客户端
SUNNY 控制面 能力目录 + 搜索发现 + 审批策略 + 短时出票 + 活动追踪
原有执行面 各业务智能体 + sidecar + 原系统数据与权限
能力有名片

Agent Card 描述技能、输入、可见范围、数据等级与接口。

访问有门闩

公开、内部、受限、待审批、停用与弃用状态决定是否出票。

调用有凭证

调用方取得绑定目标、技能和版本的 HMAC 短时票。

执行留原处

请求直达目标 sidecar，原系统继续掌握数据与最终执行。

工程架构：控制面与业务执行分离

Registry 负责“能否发现和能否调用”，sidecar 负责“验证后如何执行”。

一次跨智能体协作如何发生

  1. 登记能力

    智能体主动注册、管理台填写，或通过 Well-Known 地址同步 Agent Card。

  2. 策展审批

    管理员核对能力、数据等级和发现范围，待审批能力不向对等智能体开放。

  3. 搜索发现

    调用方通过 REST、MCP 或 Hub 按技能、标签和自然语言查询在线能力。

  4. 申请出票

    Registry 检查调用方、目标、技能、版本及策略，签发短时调用票。

  5. 直达执行

    调用方携票访问目标 sidecar，sidecar 回 Registry 验票后调用本地能力。

  6. 记录变化

    调用结果进入活动记录；Card 升版使旧票失效，停用或弃用阻止新票。

面向三类角色的价值

企业用户

找到正确能力，理解访问条件

  • 按业务问题查找已登记智能体与技能
  • 看到能力状态、适用范围和审批要求
  • 减少在多个系统间询问“谁能处理”的成本
开发人员

用稳定合同接入，不重写智能体

  • 通过 Card、REST、MCP 和 Join Packet 接入
  • 用通用 sidecar 映射本地 handler 或 HTTP 服务
  • 获得版本、心跳、探活、搜索与调用票能力
管理者

形成企业能力目录与治理视图

  • 统一查看能力归属、状态、可见范围和审批
  • 控制发布、停用、弃用与密钥轮换
  • 通过活动与调用关系追踪协作链路

当前工程成果

以下均为仓库内已实现能力。当前定位是本机与局域网验证，不宣称生产就绪。

注册与同步

管理台登记、Agent 自注册、Well-Known 拉取与周期刷新。

策展与权限

管理员、开发者角色，创建者权限，待审批、通过与拒绝流程。

发现与搜索

REST、公开卡、Extended Card、A2A 导出、MCP 和 SQLite FTS5。

安全调用

HMAC 短时票，调用方、目标、技能与 Card 版本绑定，sidecar 验票。

生命周期

心跳、探活、在线状态、停用、弃用、修订快照和 Card 变更流。

跨进程验证

lab.echo 用 HTTP 映射证明搜卡、出票、直打 sidecar。

工程验证路径 搜索技能 → 申请调用票 → 直达 sidecar → 验票 → 本地或 HTTP 执行 → 上报结果

治理边界与风险控制

SUNNY 负责原系统继续负责
能力名片、目录与版本业务数据的存储与质量
发现范围与接入审批数据行列权限与业务审批
调用资格与短时票最终动作授权与业务执行
心跳、探活和调用活动业务审计、合规留痕与责任认定
不能混淆的两件事

在目录中“看见某个技能”，只代表调用方知道该能力存在。是否能获取完整信息、是否能出票、目标系统是否执行，仍由分层策略和原系统权限共同决定。

建议的下一步

近期 强化目录治理

增加 Hub 的智能体类型分栏，完善浏览器端端到端测试，明确生产配置基线。

中期 接入真实业务试点

选择 2-3 个跨系统高频场景，验证审批、权限、失败处理与审计闭环。

后续 连接企业基础设施

评估 SSO、外置 agent gateway、高可用存储与集中可观测平台。

SUNNY 的目标不是替代每个智能体。

它让企业已经拥有的智能体能力，从“散落在系统里”变成“可发现、可审批、可调用、可治理”的共享能力网络。
